# 踩過的坑

開發 FitAI 過程中實際遇到、花時間才搞清楚的問題。按「值得記住的程度」排序，
不是按遇到的時間順序。

每一條的格式是：**症狀 → 原因 → 對策**。
會報錯的坑很好解決；這份文件的重點是**不會報錯的那些**。

---

## 一、不會報錯的失敗（最危險）

這一類共同的性質是：程式跑完、沒有例外、輸出看起來正常，但結果是錯的。
除錯時最花時間，因為你不知道要從哪裡開始找。

### 1. Embedding API 回傳順序可能與輸入不一致

**症狀**：檢索結果莫名其妙地爛，但每一層看起來都正常——向量維度對、數量對、型別對。

**原因**：`client.embeddings.create()` 回傳的 `resp.data` 順序「文件說」會對齊 input，
但沒有保證。順序一旦錯位，就會變成「大麥仁的文字配到小米的向量」。

**對策**：依 `item.index` 排序後再取 `.embedding`。

```python
for item in sorted(resp.data, key=lambda x: x.index):
    vectors.append(item.embedding)
```

一行的成本，換掉一個查不出來的 bug。

### 2. `zip` 會靜靜截短到最短的那個

**症狀**：ingest 說「寫入 2213 筆」，資料庫實際只有 2180 筆，沒有任何錯誤訊息。

**原因**：`zip(texts, metas, vectors)` 在長度不一致時直接截短，不會抗議。

**對策**：Python 3.10+ 用 `zip(..., strict=True)`，長度不符就拋 `ValueError`。

### 3. 相對日期的測試資料會讓 eval 不可重現

**症狀**：昨天 eval 跑 80 分，今天同一份程式跑 60 分。以為 prompt 改壞了。

**原因**：seed 用 `days_ago=0` 產生「今天」的資料，隔天再跑，那批就變成昨天了，
「我今天吃了什麼」查不到東西。

**對策**：`run_eval` 開頭先呼叫 `seed()` 把 fixture 重置成已知狀態。
**eval 的第一要求是可重現，不是準確。**

### 4. `append` 一整批 vs `extend`

**症狀**：型別註記說 `list[list[float]]`，實際拿到 `[[Embedding, Embedding], [...]]`。

**原因**：`vectors.append(resp.data)` 是「把整個 list 當成一個元素塞進去」。

**對策**：接一整批用 `extend`，或在內層迴圈裡一次 `append` 一個。

### 5. 「查無此人」與「這個人沒資料」輸出一模一樣

**症狀**：`summarize_food_logs(user_id=999, ...)` 回傳「這段期間完全沒有飲食紀錄」——
跟真實存在但沒記錄的使用者輸出完全相同。

**原因**：查詢用 `WHERE user_id = 999` 篩選，篩不到就是空集合。
SQL 不會告訴你「這個 id 根本不存在」，因為它沒被問到這件事。

**為什麼要在意**：對 agent 來說這是實質差異。模型看到「沒有紀錄」會鼓勵使用者
開始記錄；看到「查無此帳號」則該說系統找不到人。輸出相同，模型就無從分辨。

**對策**：查資料前先確認主體存在。

```python
if db.query(User).filter(User.id == user_id).first() is None:
    return f"查無 user_id={user_id} 這位使用者。"
```

**通則**：只要函式對「空結果」和「查無對象」有不同的正確回應，
就不能讓兩者共用同一個輸出。這在資料層很容易混為一談，
因為 SQL 對兩者的回應都是空集合。

### 6. 工具的錯誤被包裝成結果後，失敗會偽裝成「模型不聽話」

**症狀**：agent 回答「豆漿熱量大約 40-60 大卡」——資料庫明明有 35 大卡的正確資料，
模型卻用自己的記憶回答。看起來像是 prompt 的「數值必須來自工具」規則沒生效。

**實際原因**：工具**根本沒跑成功**。

```
error = search_nutrition() got an unexpected keyword argument 'user_id'
```

迴圈對每個工具都注入 `user_id`，但只有查使用者資料的工具收這個參數。
而 `_execute` 刻意把例外包裝成「給模型看的錯誤訊息」（讓它能自我修正），
所以程式不會崩、使用者也看不出異狀——模型拿不到資料，只好用記憶回答。

**對策**：用簽章判斷該不該注入，而不是另外維護一份名單。

```python
if "user_id" in inspect.signature(func).parameters:
    safe_args["user_id"] = user_id
```

**真正的教訓**：把工具錯誤轉成模型可讀的訊息是對的設計，但它會**吃掉錯誤的可見度**。
沒有工具呼叫紀錄的話，症狀會指向完全錯誤的方向——當時差點去改 prompt。

所以 agent 一定要記錄每次呼叫的 `(工具, 參數, 結果, 錯誤)`。
這也是「評估路徑而不只評估答案」的前提。

### 7. 工具缺口不會讓模型說「做不到」，它會拿最接近的工具硬湊

**症狀**：問「我**吃過**什麼蛋白質密度最高的食物」，agent 回答柴魚片、小魚干——
那些是營養資料庫裡的食物，使用者根本沒吃過。兩次工具呼叫都成功（`error=None`），
答案讀起來也很順，但**回答的是另一個問題**。

**原因**：現有工具沒有任何一個能「在使用者自己的紀錄裡排序」。

| 工具 | 範圍 | 能排序嗎 |
|---|---|---|
| query_food_logs | 使用者紀錄 | ❌ 單日明細 |
| summarize_food_logs | 使用者紀錄 | ❌ 逐日彙總，不是逐食物 |
| rank_by_nutrient | **公開資料庫** | ✅ 但範圍錯了 |

模型只能用手上有的工具拼湊，於是挑了範圍錯誤的那個。
**它不會停下來說「我缺一個工具」——那不在它的選項裡。**

**對策**：定期用真實問句測試，並檢查**路徑**而不只是答案。
這類失敗只能從「它呼叫了什麼」看出來，因為答案本身看起來完全合理。

**通則**：agent 的能力邊界是隱形的。工具清單決定了它能回答的問題範圍，
但使用者不知道那個範圍，模型也不會主動宣告。
所以問句盤點要持續做——它是把隱形邊界顯形的唯一方法。

### 8. 漏掉一個 timeout，就等於整條請求沒有 timeout

**症狀**：把 Postgres 關掉測 agent 的降級行為，結果使用者看到的是
「查詢時間過長」——**降級那條路徑根本沒被走到**。模型從頭到尾沒機會回應。

**原因**：LLM 呼叫和迴圈總時間都設了上限，但**資料庫連線沒有**。
psycopg 預設會等到作業系統放棄，而且 `localhost` 會依序試 `::1` 和
`127.0.0.1` 兩個位址、各等一次。一次工具呼叫就吃光 90 秒的迴圈預算。

**對策**：

```python
engine = create_engine(
    settings.database_url,
    connect_args={"connect_timeout": 5},
    pool_pre_ping=True,
)
```

修完之後同樣的測試從「超過 90 秒然後逾時」變成「20 秒內給出降級回答」。

**通則**：**逾時控制的強度由最弱的那一環決定。** 你設了 LLM 的 timeout、
設了迴圈的預算，但只要鏈路上有一個對外呼叫沒設，它就會成為卡住整個
請求的那一個。列出所有對外呼叫（資料庫、LLM、檢索、外部 API），
確認每一個都有明確的上限。

`pool_pre_ping=True` 是附帶加的：連線借出前先 ping 一次，回收掉
已經斷掉的舊連線（例如資料庫重啟過）。代價是每次查詢多一次極輕量的往返。

### 9. Agent 的自主判斷，會放棄固定流程原本無條件會做的事

**症狀**：問「我吃的那個叫什麼粿的熱量多少？」，agent 一個工具都沒呼叫，
直接回「不太明確，請提供更具體的名稱」。同一題在舊的固定流程下是成功的。

**原因**：固定流程的檢索是**無條件執行**的——粉粿、芋頭粿早就在 context 裡，
模型只要照著報。換成 agent 之後，「要不要查」變成模型的判斷，
而它在**還沒查之前**就認定「太模糊所以查不到」。

諷刺的是，語意檢索正是為了處理模糊名稱而存在的（俗名寫進 content 就是
為了讓「洋薏仁」找到「大麥仁」），模型卻在用它之前就先放棄。

**對策**：prompt 明講「模糊名稱也要先查再說」，並說明理由——

```
不要在還沒查之前就判斷「太模糊所以查不到」
——那等於放棄了這個工具最擅長的事。
```

**通則**：從固定流程換成 agent，是把「一定會發生的事」變成「模型決定要不要做」。
**每一個原本無條件執行的步驟，都可能被跳過**，而且跳過時不會有任何錯誤。
換架構時要逐項檢查：原本必定發生的事，現在還會發生嗎？

### 10. 換架構會帶來系統性回歸，不是單一題的意外

**症狀**：eval 從固定流程改成跑 agent 之後，8 題裡有 4 題的答案長度超標
（285、239、279、280 字，上限 200）。

**原因**：工具回傳的是結構化 JSON，資訊量比檢索回來的文字 chunk 豐富得多，
模型傾向把查到的五項食物全部列出來——光列表就超過限制。

**對策**：找出真正的驅動因素再對症下藥。這裡不是「廢話太多」而是「列太多項」，
所以限制項數（「最多列 3 項」）比限制字數有效——**數項目比數字容易，
模型比較遵守得了**。同時把上限放寬到 300，因為列三項加說明確實需要那個長度。

改完之後四個長度失敗全部消失。

**通則**：換架構時不要只確認「新功能會動」，要**跑完整的回歸**。
單題測試會讓你以為只是偶發，跑完整套才看得出「8 題裡有 4 題」這種系統性模式。

### 11. 跨層的狀態旗標，沒有一路傳上來就等於不存在

**症狀**：把 Postgres 關掉打 `/chat`，agent 正確降級、回答也得體，
但回應裡的 `degraded` 是 `False`——前端會以為一切正常，不會提示使用者
有部分功能不可用。

**原因**：失敗的訊號在中途斷掉了。

```
_ToolOutcome.unavailable = True      ← 工具層知道
        ↓
ToolCall（沒有這個欄位）              ← 斷在這裡
        ↓
AgentResult.error = None             ← 只有迴圈本身失敗才設值
        ↓
API 層看不出有任何問題
```

`AgentResult.error` 只在**迴圈本身**失敗時才有值（最外層攔截、超過時間預算）。
個別工具失敗不會讓迴圈失敗——那正是降級設計的目的——但也因此，
API 層失去了「有東西壞掉」的資訊。

**對策**：把 `unavailable` 加進 `ToolCall`，API 層才判斷得出來。

```python
degraded = result.error is not None or any(c.unavailable for c in result.tool_calls)
```

**為什麼不能直接看 `ToolCall.error`**：那個欄位對「模型參數給錯」和
「重複呼叫」也會設值，兩者都不算服務降級。**需要的是專門的旗標，
不是拿現成的欄位湊合**——語意不同的東西共用一個欄位，遲早會誤判。

**通則**：分層架構裡，每一層都會決定「什麼要往上傳」。降級設計刻意讓
下層的失敗**不要**往上變成例外，但這樣一來，上層就需要**另一條明確的通道**
才知道發生過什麼。設計降級時要同時問：「上層要怎麼知道？」

這類 bug 單元測試抓不到——它跨了工具、迴圈、API 三層，每一層單獨看都正確。
只有真的把依賴關掉、真的打一次 API 才會浮現。

### 12. 「走了兩步」不等於「第二步用了第一步的結果」

**症狀**：問「我今天熱量還剩多少？可以吃什麼點心？」，agent 確實走了兩步，
答案裡的「還剩 380 大卡」也正確。路徑判準全部通過。但看參數：

```
query_food_logs(days_back=0)
rank_by_nutrient(nutrient="sugar_g", max_calories=150)
                                      ↑ 不是 380
```

`150` 是 docstring 裡「低卡」的建議門檻，**模型沒有把第一步算出的剩餘額度
接進第二步的參數**。答案裡引用了 380，工具呼叫卻沒用上它。

**為什麼危險**：這正是「有限迴圈 tool calling」這個架構決策的唯一依據。
如果多步只是「連續呼叫兩個工具」而沒有真正的資料依賴，那**路由就夠了**，
迴圈的成本白付。而只看路徑的話，這件事完全看不出來。

**路徑判準抓不到它**：

```
required_tools: [query_food_logs, rank_by_nutrient]   ✅ 通過
order:          [query_food_logs, rank_by_nutrient]   ✅ 通過
max_calls:      3                                     ✅ 通過
```

三條全過，但參數是錯的。

**對策**：加**參數斷言**。路徑判準檢查「呼叫了什麼」，還需要一層檢查
「帶了什麼參數」——例如「`max_calories` 應接近第一步結果中的剩餘額度」。

**通則**：**評估的粒度決定你看得到什麼。**
答案層看不到工具選擇，路徑層看不到參數正確性。每加一層都會揭露一批
先前隱形的失敗——而你不會知道還有幾層沒加，直到實際去看那一層的資料。

順帶一提，同一次呼叫裡 `nutrient="sugar_g"`（依糖分排序找點心）的推理也很可疑，
結果碰巧可用而已。這類「答案對但推理錯」只有逐項檢查參數才會浮現。

### 13. 工具只支援一個方向時，模型會硬用，然後把結果講反

**症狀**：問「我這週吃太多醣了嗎？有什麼低醣的可以換？」，agent 呼叫
`rank_by_nutrient(nutrient="carbs_g", max_calories=150)`，拿到**碳水最高**的
前三名，然後在答案裡寫「以下是三種碳水化合物含量較低的食物推薦」。

**原因**：那個工具當時只能由高到低排序，沒有 `order` 參數。
模型需要「最低」但工具只給得出「最高」——**它沒有拒答，而是照用不誤，
再在敘述層把結果講成相反的意思。**

**為什麼比拒答危險**：拒答至少誠實。這種失敗會給出一份看起來完全合理、
數字也真實存在的清單，只是意義整個相反。使用者沒有任何線索可以察覺。

**對策**：補上 `order` 參數（`desc` / `asc`），並在 docstring 與 JSON Schema
兩邊都明講什麼時候用哪個：

```
order: 這個參數決定你拿到的是最高還是最低，不要用錯。
       desc 用於「高蛋白」「纖維最多」；asc 用於「低醣」「低鈉」「最少」。
       用錯方向會拿到完全相反的清單，而它看起來仍然很合理。
```

**通則**：**檢查每個工具的「對稱性」**——支援最大值就該支援最小值、
支援升冪就該支援降冪、支援新增就該想到刪除。
缺了一半的話，模型不會提醒你，它會用手上有的那一半硬湊，
然後在自然語言層把差異抹平。這類缺口只有實際問「相反方向」的問題才會浮現。

## 二、向量檢索的本質限制

### 14. 語意檢索不會比較數值大小

**症狀**：查「高蛋白質的食物」，撈回鴨蛋白（10.8g）、雞蛋白（10.7g）——
而資料庫裡真正高蛋白的是柴魚片（76.5g）。

**原因**：向量比對的是「語意相似度」。「蛋白質」和「蛋白」在字面與語意上高度重疊，
模型被字面帶走。它從來就不理解「高」是一個數值比較。

**對策**：這類問題**不該用向量檢索**。改用 metadata 的數值排序：

```sql
SELECT content FROM knowledge_chunks
WHERE (meta->>'calories')::float < 150
ORDER BY (meta->>'protein_g')::float DESC LIMIT 5;
```

**延伸**：reranking 和 hybrid search（BM25）都救不了這題。
BM25 只會讓「蛋白」權重更高，錯得更徹底。改架構之前先確認病灶在哪。

### 15. content 怎麼組，比用什麼演算法重要

食藥署資料的兩個實例：

- **俗名有 40% 缺值，但有值時極重要。** 「大麥仁」的俗名是「小薏仁,洋薏仁,珍珠薏仁」。
  使用者打「洋薏仁」時，content 裡沒有這幾個字就永遠檢索不到。
- **樣品狀態決定數值對不對。** 「雞腿菇」35.8 大卡 vs「雞腿菇(乾)」297.6 大卡，
  差 8 倍，差別只在描述裡的「生」與「乾貨」。這欄不寫進 content，
  檢索回來的熱量會錯得離譜。

**對策**：ingest 之前先實際看資料的缺值分布與欄位語意，再決定 content 要放什麼。
這比調 chunk size 或換 embedding model 的效益大得多。

## 三、LLM 的不確定性

### 16. 同一個 prompt，不同次執行會有不同行為

**實測**：問句「我吃的那個叫什麼粿的熱量多少？」三次執行——

| 執行 | 結果 |
|---|---|
| 8/30 | ✅ 列出粉粿、芋頭粿與熱量 |
| 8/31 | ❌ 拒答「找不到相關資料」 |
| 9/02 | ✅ 列出候選 |

prompt 一個字都沒改。**單次執行的結果不能當結論。**

**對策**：重要的判斷要跑 N 次看通過率，而不是跑一次看對錯。

### 17. `temperature=0` 不保證穩定

**症狀**：LLM-as-Judge 對同一列給出不一致的判定。

**實測**：同一個輸入各跑 5 次——

```
預設溫度(1.0)   {'pass': 5}
temperature=0   {'pass': 2, 'fail': 3}
```

`temperature=0` 反而更不穩定。原因是這個判定本身落在**決策邊界**上，
而判準寫得模糊（「有說明份量假設」可解讀成「寫出份量」或「明講是假設」）。

**對策**：不穩定時先檢查**判準是否模糊**，不要急著調參數。
把判準改成「回答有明確寫出換算所使用的份量」之後就穩定了。

### 18. 規則修邏輯，範例修風格

**症狀**：prompt 裡寫了「不要提及使用者的飲食紀錄」，模型還是提了。

**原因**：那是**風格問題**不是邏輯問題。抽象規則對風格的約束力很弱。

**對策**：給一個 few-shot 範例，模型立刻照做。

```
Q：豆漿的熱量是多少？
A：無糖豆漿每 100 公克約 35 大卡 [1]，一杯 300ml 大約 105 大卡。
```

一個範例同時示範了：不提使用者紀錄、用「你」稱呼、引用格式、長度。

### 19. 過度嚴格的規則會造成過度拒答

**症狀**：檢索明明撈到粉粿和芋頭粿，模型卻回答「找不到相關資料」。

**原因**：prompt 寫了「絕對不要把營養資料庫的食物說成使用者吃過的」，
模型過度延伸成「連一般知識都不敢回答」。

**對策**：規則要區分情境。加上「問題類型判斷」——
一般知識問題只用資料庫回答、個人問題才看飲食紀錄。

### 20. 要求引用來源，能讓幻覺變得可稽核

**症狀**：模型回答「雞胸肉每 100g 含 31g 蛋白質」——資料庫裡沒有這筆，
而且跟資料庫的 24.8g 矛盾。要查證才知道是編的。

**對策**：在 context 給每筆 chunk 編號，要求引用時標註 `[n]`。

改變的不是「會不會出錯」，而是**錯誤的性質**：從「查不出來的編造」變成
「可以順著編號查證的引用」。而且引用標記可以用正則自動檢查。

### 21. 給模型的提示訊息，本身就是 prompt

**症狀**：重複呼叫的偵測反而讓答案變糟。模型第二次呼叫同樣的工具時，
迴圈回傳「這個查詢剛才已經做過了，結果如上」——模型接著就說「查無資料」，
改用自己的記憶回答。

**原因**：那句話是**寫給人看的**。模型讀到它，理解成「查詢沒有結果」，
而不是「去看前面那則訊息」。

**對策**：重複呼叫時回傳**快取的原結果**，不要回提示訊息。

語意上也更誠實——這個查詢的答案就是這個，再問一次答案不會變。

**通則**：任何會進到 messages 的字串都是 prompt，包括錯誤訊息、
狀態提示、佔位符。寫的時候要問「模型看到這句話會怎麼理解」，
而不是「這句話對人來說清不清楚」。

## 四、Eval 方法論

### 22. 整體一致率在類別不平衡下會騙人

**問題**：如果 90% 的輸出本來就是好的，一個「永遠回答 pass」的 judge
一致率就有 90%——但它完全沒用。

**對策**：分開看兩個方向，再用 Cohen's kappa 扣掉隨機一致。

| 指標 | 意義 |
|---|---|
| TPR | 人工判 fail 的，judge 抓到幾成（會不會漏放） |
| TNR | 人工判 pass 的，judge 沒誤報幾成（會不會亂咬） |

對 eval 的判官來說，**TPR 比 TNR 重要**——漏放會讓你以為系統沒事，
誤報只是多看幾筆。

### 23. 否定式判準會讓 judge 判反

**症狀**：判準寫「沒有提及今日飲食紀錄」，judge 的理由是
「答案沒有提到飲食紀錄」，然後判 **fail**。

**原因**：它把「觀察到判準描述的情況成立」當成了違規。

**對策**：判準一律用肯定式描述「通過時應有的狀態」：

```
沒有提及今日飲食紀錄
  ↓
回答內容完全來自營養資料庫，與使用者個人飲食紀錄無關
```

### 24. 判準必須正交

**症狀**：同一個缺陷被兩條判準各扣一次分，失敗率虛高。

**實例一**：「所有被稱為高蛋白的食物須 ≥20g」和「每項食物都有檢索資料佐證」
同時懲罰「推薦了資料庫裡沒有的豆腐」。

**對策**：把其中一條收窄範圍，讓兩條各司其職。
前者改成「所有**從檢索資料中挑出**、被稱為高蛋白的食物…」。

**實例二（2026-09-22，同一個坑又踩了一次）**：known_gap 那題三條 rubric 全判 fail，
看起來像三個獨立的問題，實際上只有一個缺陷——agent 把資料庫的柴魚片
講成使用者吃過的：

```
沒有把營養資料庫裡的食物說成使用者吃過的   ← 這條命中要害
有說明目前無法針對吃過的食物做排序        ← 同一個缺陷的另一面
沒有列出工具結果以外的食物名稱            ← 字面上根本沒違反（柴魚片就在工具結果裡）
```

第三條連 judge 都判 pass，而且**它是對的**——柴魚片確實在 `tool_results` 裡。
人工判 fail 用的理由（「那不是使用者吃過的」）其實屬於第一條。
已改寫成「沒有謊稱查詢結果涵蓋了使用者的飲食紀錄」，問一件獨立的事。

**後果**：一個缺陷貢獻三個 fail，統計會以為系統有三個問題。通過率、TPR、TNR
全部失真，而且是往「看起來更糟」的方向——修好那一個缺陷，分數會跳三格，
讓人誤以為改善幅度很大。

**檢查方法**：寫完問自己「**如果只修好 A，B 會不會自動變成 pass？**」
會的話，兩條該合併。

**通則**：**評分標準的獨立性，跟它的正確性一樣重要。**
一堆彼此重疊的 rubric 會放大雜訊，讓你分不清「一個大問題」和「很多小問題」。

### 25. 每次盯著資料修東西，那份資料就變成訓練資料

**症狀**：留出集跑出 100%，但那是因為我已經看著它修過兩次判準。

**原因**：這是統計上的老問題——**在測試集上調參**。

**對策**：資料集夠大時切出一批完全不看的樣本，只在階段性驗收時跑一次。
資料集還小的時候（<10 題），誠實的作法是**在報告數字時標註污染狀態**，
而不是假裝那是泛化能力。

### 26. 自動檢查的第一版一定不準

**症狀**：「數值有出處」規則示警兩次，兩次都是假警報——
`105`（= 35 × 3）和 `32`（= 96 − 64）都是合理的算術推導。

**對策**：兩件事。
一是**允許一步四則運算**（只允許一步，兩步以上任何數字都能湊出來）。
二是把還沒驗證過的規則列為 **warn 而非 fail**，避免它污染通過率、
久了讓人忽略所有警告。規則累積足夠精準度後再升級。

### 27. Judge 會反過來抓出人工標註的錯

校準時發現 judge 與人工不一致，追查後是**人工標錯了**——
同一題三條判準裡兩條標 fail、一條標 pass，邏輯上不一致。

校準是雙向的：你修 judge，judge 也幫你修標籤。

### 28. 「只評答案」在任何架構下都不夠，不是只有 agent 才要評中間層

**容易誤以為的事**：固定流程只有一條路徑，所以答案對就代表系統對；
要到換成 agent、有工具可選之後，才需要評估「中間發生了什麼」。

**這是錯的。** 固定流程一樣會「答案對但內部壞掉」。

**實例**（2026-08-27 實際發生）：

```
Q: 有什麼高蛋白低卡的食物？
A: 雞胸肉每 100g 含 31g 蛋白質…
```

答案讀起來完全正確——雞胸肉確實是高蛋白。但 31g 是模型從記憶裡拿的，
跟資料庫的 24.8g 矛盾；而檢索當時撈回來的其實是一堆蛋白（10.7g）。
**檢索壞了，只看答案完全看不出來。**

**正確的框架**：任何 LLM 管線都要評中間層，差別只在中間有什麼可評。

| | 要評的層 |
|---|---|
| 固定流程 | 檢索結果品質、答案有沒有基於它（groundedness） |
| Agent | 以上全部 **＋ 工具選擇（trajectory）** |

Agent 是**多了一層**，不是從「不用評」變成「要評」。

**兩種「路徑錯」的性質不同**：

```
固定流程：檢索撈到蛋白(10.7g)           ← 有撈，但撈得爛（品質問題）
Agent：  判斷「太模糊」直接不撈          ← 根本沒撈（結構問題）
Agent：  用 rank_by_nutrient 撈錯範圍    ← 撈了，但撈錯地方（結構問題）
```

後兩種在固定流程裡不可能發生，因為步驟是寫死的。

**對策**：固定流程時期就要有 groundedness 檢查（答案裡的數值能否在檢索結果中
找到），換 agent 時再疊上軌跡判準。這兩層分別對應 RAG triad 的
context relevance / groundedness，以及 agent 特有的工具選擇。

## 五、資料型別與序列化

### 29. JSONB 存不下 NaN

**症狀**：commit 時噴 `TypeError`，或存進去之後讀不回來。

**原因**：JSON 標準沒有 NaN 這個值。`json.dumps(float('nan'))` 產出的
字面 `NaN` 不是合法 JSON。

**對策**：`None if pd.isna(value) else float(value)`。

### 30. numpy 的 `float64` 不能被 json 序列化

同一行的另一半：`float()` 不只是防禦性轉型，是必要的——
pandas 取出的數值可能是 `numpy.float64`，`json.dumps` 不認識它。

### 31. `NaN != NaN`

**症狀**：用 `== None` 或 `is None` 判斷缺值，永遠判不到。

**原因**：IEEE 754 規定 NaN 不等於自己。

**對策**：用 `pd.isna()`。

### 32. content 與 meta 對缺值的處理應該相反

- **content**（給人和 LLM 讀的散文）：缺值**整項跳過**。
  不能出現「含膳食纖維 nan 公克」。
- **meta**（給程式讀的結構）：缺值**保留 key、值設 None**。
  這樣讀取端不會 `KeyError`，而且 `None` 明確表達「這項沒測」，
  跟「我忘了存這欄」區分得開。

同一份資料，兩種用途，兩種正確做法。

## 六、時區與日期

### 33. `timestamp without time zone` 遇上「今天」

**症狀**：查「我今天吃了什麼」，早餐不見了。

**原因**：`logged_at` 存的是 naive UTC，但使用者說的「今天」是台北時間的今天，
差 8 小時。直接用 UTC 的 00:00 當界線，會把**台灣時間早上 8 點前**的紀錄
算成前一天——而早餐正好落在這個區間。

**對策**：先在本地時區組出邊界，轉成 UTC，再脫掉 tzinfo。**順序不能顛倒**：

```python
dt.astimezone(timezone.utc).replace(tzinfo=None)   # ✅ 先換算，再脫標籤
dt.replace(tzinfo=None).astimezone(timezone.utc)   # ❌ 先脫標籤 → 時刻跑掉
```

`astimezone()` 是換算時刻，`replace(tzinfo=None)` 只是拔掉標籤、數字不動。

**根治**：欄位改成 `timestamptz`。但那是 schema 變更，需要 migration。

## 七、工具鏈的小坑

這些會直接報錯，查一下就解決，記錄下來只是為了下次快一點。

| 症狀 | 原因 | 對策 |
|---|---|---|
| `Relative module names not supported` | `python -m` 後面接了路徑 | 用點號模組名：`python -m app.rag.qa` |
| `ModuleNotFoundError: No module named 'app'` | 用檔案路徑跑，`sys.path[0]` 變成檔案所在目錄 | 一律用 `-m`，並在 `backend/` 執行 |
| 模組 docstring 失效（`__doc__` 是 None） | import 被放在 docstring 上面 | docstring 必須是檔案的第一個敘述 |
| `f-string: single '}' is not allowed` | f-string 裡有沒配對的 `}` | 檢查是否漏了左大括號 |
| f-string 裡的函式呼叫變成字面文字 | 運算式寫在 `{}` 外面 | 整個運算式要進大括號：`{round(x, 1)}` |
| `str(list)` 得到 `['a', 'b']` 這種東西 | `str()` 作用在容器上產生的是 repr | 用 `"".join(...)` |
| `AttributeError: 'DataFrame' object has no attribute 'limit'` | `.limit()` 是 Spark/SQL 的方法 | pandas 用 `.head()` |
| `df.head(None)` 型別檢查報錯 | 執行期可以，但簽章宣告是 `int` | 顯式寫 `if limit is not None` |
| instructor 包過的 client 沒有 `.embeddings` | instructor 只暴露 chat.completions | embedding 另開一個純 langfuse 包裝的 client |
| 讀 Excel 欄位全是 `Unnamed: N` | 第一列是說明文字，不是表頭 | `pd.read_excel(..., header=1)` |
| 連不上 5432 | Docker 容器重開機後停掉 | `docker start fitai-postgres` |

## 八、可重現性：能在我的電腦上跑，不等於能跑

這一節的兩條都是 2026-09-22 寫整合測試時踩到的。
共同點是：**開發機上一切正常，因為錯的那個狀態早就在本機建好了。**

### 34. 只存在資料庫裡的 prompt，等於不在版控裡

**症狀**：`POST /food_logs` 在乾淨的資料庫上直接 500，
log 裡是 `ValueError: 找不到 name='food_extraction_system_prompt' 的 prompt version`。

**原因**：`prompt_versions` 表讓 prompt 可以不改程式、不重新部署就換版——
這個設計是對的，但那份 prompt 的內容**只有**在資料庫裡。
它是幾個月前手動 INSERT 進去的，程式碼、文件、git 都沒有留下任何一個字。
本機的 volume 一被重建，內容就永遠消失了；別人 clone 下來更是從一開始就沒有。

危險的地方在於它**平常完全不會現形**：開發機的資料庫裡有那筆資料，
所有手動測試都會通過。要嘛換機器、要嘛重建 volume、要嘛別人 clone，才會爆。

**對策**：把基準版本放進版控（`app/prompts.py`），由 `init_db` 在
「這個 name 一筆版本都沒有」時寫成 version 1。
執行期換版的彈性完全保留——`add_prompt_version` 加的版本號較大，會蓋過基準版。

**通則**：**執行期可以覆蓋的設定，也要有一份在版控裡的預設值。**
可覆蓋不等於可以沒有。同一個檢查適用於：feature flag、模型名稱、
閾值、系統提示詞——任何「決定系統行為、但不在程式碼裡」的東西。

### 35. 客戶端給錯資料，卻回 500

**症狀**：`POST /food_logs` 帶一個不存在的 `user_id` → 500
（`{"error": {"code": "internal_error"}}`）。

**原因**：端點沒有檢查使用者存在，直接 INSERT。
外鍵約束是在 `db.commit()` 那一刻才由資料庫拒絕的，拋出的是
`IntegrityError`，被全域 handler 當成未預期例外接走，變成 500。

兩個獨立的問題：

1. **狀態碼說錯話。** 500 的語意是「伺服器壞了，稍後重試」，
   但這是客戶端給錯資料，重試一萬次也不會成功。
2. **白花一次 LLM 呼叫。** 驗證在 INSERT 時才發生，而 `extract_food_log`
   在那之前就跑完了——花了錢、產出的結果注定要丟掉。

**對策**：在昂貴的呼叫**之前**顯式檢查，回 404。

```python
if db.get(UserModel, payload.user_id) is None:
    raise HTTPException(status_code=404, detail="User not exist")

extraction = extract_food_log(payload.raw_text)   # 昂貴的呼叫在後面
```

**通則兩條**：
- **便宜的驗證放在昂貴的呼叫前面。** 順序不只影響效能，也影響帳單。
- **不要靠資料庫約束當作 API 的驗證層。** 約束是最後一道防線，
  它報錯的形式是資料庫例外，而那翻譯不成對使用者有意義的訊息。

### 36. 整合測試要能在沒有 Docker 的情況下跑完

**症狀**（這條是預防而非事後）：測試如果需要先 `docker compose up`、
先跑 seed、先設 `OPENAI_API_KEY`，那它就會變成「有空才跑」的測試，
也就等於沒有測試。

**對策**：這層測試用 SQLite in-memory 取代 Postgres、用假的函式取代 LLM
與 agent。端點的契約（狀態碼、回應形狀、降級判斷、欄位對應）不需要真的
依賴就測得到。45 個測試跑完不到 1 秒、不花任何錢。

**代價要講清楚**：這層**測不到** Postgres 特有的東西——JSONB 查詢、
pgvector 相似度、`statement_timeout`、外鍵約束（SQLite 預設不強制）。
所以 `knowledge_chunks` 那張表在測試裡根本不建。
那些留給 eval 在真的資料庫上驗證。

**通則**：**知道一層測試「測不到什麼」，跟知道它測到什麼一樣重要。**
只講涵蓋率不講盲點，會讓人以為綠燈代表系統是好的。

## 九、評測工具本身也會壞

前面八節講的都是「被評測的系統」出問題。這一節是 2026-09-22 校準 judge 時
發現的另一類：**尺本身壞了，而量出來的數字看起來完全正常。**

這比系統出錯更危險——系統錯了你會看到爛答案，尺錯了你只會看到一個數字。

### 37. 架構換了，judge 的證據來源沒跟著換

**症狀**：judge 校準的 Cohen's kappa 只有 0.40，TNR 68%——19 個人工判 pass
的項目裡，judge 誤報了 6 個。看起來像「judge 太嚴格，要調 prompt」。

**原因**：`calibrate.py` 用 `build_contexts(question)` 重跑**舊的固定流程檢索**，
把結果當成證據餵給 judge。但答案是 **agent** 產生的，它自己選工具。
兩邊看的根本不是同一份資料。

問「有什麼高蛋白低卡的食物」時：

```
agent 實際用 rank_by_nutrient  → 雞絞肉 27.44g、雙髻鯊 27.35g、小羊腰脊肉 26.48g
judge 拿到的（語意檢索）        → 鴨蛋白 10.8g、雞蛋白 10.7g、烏骨雞蛋白 10.6g …
```

judge 於是判定「答案提到的食物都不在證據裡」→ 編造 → fail。
**它的推理完全正確，只是前提是錯的。**

更諷刺的是，那份錯誤的證據正是本文件 #14 記錄的語意檢索限制——
`rank_by_nutrient` 這個工具就是為了繞開它才做的。結果 judge 反而被它絆倒。

**對策**：judge 一律用**歸檔的**證據，不重跑。CSV 的 `tool_results` 欄
存的就是 agent 當時看到的全部（呼叫參數 + 工具回傳）。

```python
evidence = row["tool_results"]          # 歸檔的，不重跑
```

改完重跑：kappa 0.40 → **0.69**，TNR 68% → **94%**，假警報從 6 個降到 1 個。

**通則**：**answer 不能重跑，證據也不能重跑。** 這件事在 `judge_rubric` 的
docstring 裡本來就寫了（「不要重跑 QA，同一題不同次執行的答案會變」），
但只寫在 answer 上。證據被當成「可重現所以可以重算」——**在固定流程下成立，
換成 agent 就不成立了**，因為 agent 自己決定去拿什麼。

**更一般的通則**：換架構時，要盤點的不只是被換掉的東西，
還有**所有對它做過假設的周邊工具**。這一條跟 #34、#35 是同一種病——
兩邊各自都對，接縫沒跟著改，而且不會報錯。

### 38. eval 在考 prompt 從來沒教過的事

**症狀**：三條「數值要有引用標記」的 rubric 全部 fail，L1 一條都沒抓到。
看起來像 agent 表現差，或 L1 規則不夠。

**原因**：**`SYSTEM_PROMPT` 裡根本沒有要求引用標記。** 從頭到尾一個字都沒提。
工具倒是有回傳 `source_ref`（食藥署整合編號），資料一直都在，
只是沒有人叫 agent 用它。

所以這不是「做得不好」，是**規格沒對齊**：dataset 定義的期望，
沒有寫進 prompt。100% 的失敗率是這個落差的必然結果，不是模型的能力問題。

**對策**：這種落差只有兩種收法，**必須擇一**，不能放著：

1. **prompt 補上要求**——如果這個行為真的要，就明確寫進去，
   然後補一條 L1 正則檢查（引用標記是格式，正則又快又準又免費，不該給 judge 做）
2. **拿掉那幾條 rubric**——如果其實不需要

放著不動是最糟的：eval 會**永遠**回報一批修不好的失敗，
久了你就學會忽略它們——而那正是 eval 失去作用的起點。

**通則**：**eval 的每一條 rubric，都應該對應到 prompt 或程式裡的一條規則。**
找不到對應的那條，不是系統有 bug，是你們對「什麼叫做對」沒有共識。
定期反過來對一次：prompt 的每條規則有沒有人在測？
每條 rubric 有沒有對應的要求？兩邊都會漂移。

### 39. judge 會漏看答案的第一句，而且對措辭敏感

**症狀**：known_gap 那題的答案開頭寫著

> 「**根據你過去一週的飲食紀錄**，我找到幾種蛋白質密度較高的食物：柴魚片…」

那三樣是營養資料庫的排名，使用者根本沒吃過。judge 卻判 pass，理由是

> 「回答中並未明確聲稱這些結果來自用戶實際的飲食紀錄」

**它漏看了第一句**，而且在兩次獨立呼叫裡都漏看。

更值得注意的是：同一條 rubric 在前一批（09/17）**有**抓到。
答案的實質問題一模一樣，只是措辭從「最近一週你吃過的…」換成
「根據你過去一週的飲食紀錄…」，判定就翻面了。

**原因**：judge 也是 LLM，#16 那條（同一個 prompt 不同次執行會有不同行為）
對它一樣成立。校準過的 judge 不等於可靠的 judge——kappa 0.69 是**平均**表現，
它不保證任何**單一類別**的表現。而這個系統最危險的類別（捏造個人紀錄）
剛好就是它表現最差的那個。

**對策**：不要讓 judge 單獨守住高風險的類別。這題每一次都被 L1 的路徑判準
擋下來（`forbidden_tools: [rank_by_nutrient]`），因為路徑是確定性的、
不受措辭影響。**能寫成確定性規則的就別交給 judge。**

**通則**：**三層 eval 不是備份關係，是互補關係。**
L1 守得住 judge 守不住的（措辭無關的結構性錯誤），
judge 守得住 L1 守不住的（需要判斷力的內容問題）。
看 kappa 決定「要不要用 judge」是錯的問法，該問的是
「**哪一類該交給它、哪一類不該**」。

### 40. 系統修得越好，judge 越難校準

**症狀**：09/17 那批 25 列人工標註有 7 個 fail，kappa 0.69。
修完引用標記等問題後，09/22 那批只剩 **4 個 fail**，kappa 掉到 0.50。

看起來像 judge 退步了。實際上是**分母崩了**：TPR = 抓到的 fail / 人工判 fail 的總數，
分母是 4 的時候，一列翻面就是 25 個百分點。那個數字量不出任何東西。

**原因**：校準需要兩類樣本都夠多。系統變好會讓「真失敗」這一類自然枯竭——
**你越成功，越沒有東西可以驗證你的驗證工具。**

這跟 #22（整體一致率在類別不平衡下會騙人）是同一個病根——**類別比例**。
那條講的是 pass 太多會讓一致率虛高，這條講的是 fail 太少會讓 TPR 算不出來。
同一份標註集，兩個方向都會出問題。

**對策**：刻意構造失敗案例，不要等系統出錯。歷史上真的出現過的壞答案
（本文件和 `question_inventory.md` 裡有一整批）連同 rubric 一起放進 dataset——
那些答案歸檔的 CSV 裡就有，不需要重新產生。

**通則**：**gold standard 的類別平衡是要維護的，不會自己保持。**
一份只有好例子的標註集，能告訴你 judge 不亂咬（TNR），
完全不能告訴你它抓不抓得到問題（TPR）——而後者才是 eval 的存在理由。

## 十、同一個系統裡的兩條路徑，可靠性標準不該不同

2026-10-16 使用者在前端輸入「早上喝了一杯鮮奶茶」，系統記錄 **50 大卡**。
一路追下去挖出五個相關的坑，而起點只是一句「這合理嗎？」

### 41. 嚴格的規則只套在一條路徑上，另一條就成了破口

**症狀**：一杯鮮奶茶記成 50 大卡，真實約 133 大卡（資料庫「鮮奶茶(無糖)」
26.5 大卡/100g × 500 毫升）。**低估 2.6 倍，而且不會報錯**——
使用者只會以為自己喝的東西很健康，每日合計就這樣系統性偏低。

**原因**：問答側的 prompt 守得很嚴——「所有具體的營養數值都必須來自工具回傳的
結果」「推薦具體食物時，食物名稱也必須來自工具結果」。但**記錄側完全沒有這個要求**：
`extract_food_log` 讓 LLM 同時負責「這是什麼」與「有多少熱量」，後者純靠它自己猜。

2213 筆食藥署資料就在那裡，問答用得很勤，記錄這條路徑**一次都沒用到**。

**對策**：記錄也改成兩階段，讓 LLM 只做語言、數字盡量來自資料庫：

```
① LLM 解析    raw_text → [{名稱, 份量公克}]      不估營養素
② 檢索        每項 search(名稱, top_k=5)
③ LLM 配對    給它候選，選出相符的 source_ref，沒有就回 null
④ Python 算   有佐證：資料庫數值 × 份量/100；無佐證：用 LLM 的估算
```

**通則**：**同一個系統裡，不同入口的可靠性標準要一致。**
你為某條路徑訂了嚴格規則，就要問「另外那幾條呢」——
沒被規則覆蓋的那條會變成整個系統的上限，而它通常是比較少人看的那條。

### 42. 「無糖」會觸發模型的低熱量捷思

**症狀**：同一杯飲料，說「鮮奶茶」模型估 300 大卡（合理），
說「無糖鮮奶茶」估 50 大卡（離譜）。明確給了 500ml 也只估 75 大卡。

**原因**：模型把「無糖」當成「接近零熱量」，忽略鮮奶本身就有 64 大卡/100ml。
看它給的蛋白質就知道——3 公克蛋白質約等於 90 毫升鮮奶，它根本沒把一杯的量算進去。

**對策**：不要靠改 prompt 去糾正這類捷思（那是打地鼠）。
**把數字的來源換掉**才是根治——改成查資料庫之後，「無糖」只影響它配對到
哪一筆（鮮奶茶(無糖) 而不是鮮奶茶），不再影響熱量怎麼算。

**通則**：**修辭會改變 LLM 的數值判斷。** 「無糖」「低卡」「輕食」「健康」
這些詞會系統性地把估計值往下拉。靠 prompt 逐一堵不完，
治本的方法是讓數值不要由模型產生。

### 43. 配錯比沒配到更糟，而且會被份量放大

**症狀**（改完之後跑出來的新錯誤，比原本的 bug 嚴重）：

```
一碗滷肉飯 → 配到「臘肉(五花肉)」525 大卡/100g × 500g = 2625 大卡
一個漢堡   → 配到「漢堡包」（麵粉,糖,奶油,酵母…沒有肉）322 大卡/100g × 200g = 644 大卡
鮪魚蛋吐司 → 配到「鮪魚肚」106 大卡/100g
```

**原因**：複合餐點在資料庫裡不存在，但檢索**一定會回傳東西**，而且回傳的是
名稱最像的單一食材。LLM 看到「滷肉飯」和「臘肉」都是滷的豬肉就配了，
然後程式用**整碗飯的重量**去乘**五花肉的熱量密度**——錯誤被份量放大了四倍。

這是 #14（語意檢索不會比較數值）的近親：檢索的輸出永遠「看起來合理」。

**對策**：prompt 寫「寧可判不相符」擋不住，要在程式層加一道確定性的防線。
用名稱的雙向字元覆蓋率當門檻（`app/extraction.py` 的 `name_matches`）：

```
無糖鮮奶茶  ↔ 鮮奶茶(無糖)     0.60  ✓ 接受（只是詞序與修飾語不同）
鮪魚蛋吐司  ↔ 鮪魚肚           0.40  ✗ 拒絕
漢堡        ↔ 冷凍牛肉漢堡肉   0.33  ✗ 拒絕
一碗滷肉飯  ↔ 臘肉(五花肉)     0.33  ✗ 拒絕
```

**單向覆蓋率不夠**：「漢堡」的每個字都在「冷凍牛肉漢堡肉」裡，
但後者多出「冷凍牛肉」，那表示它是另一種東西。要取兩個方向的較小值。

**這道防線刻意只能「拒絕」，不能憑空產生佐證。**
誤拒的代價是少一個有來源的數值（退回改版前的行為），
誤收的代價是一個錯四倍、看起來卻很權威的數字。兩者不對稱，所以寧可誤拒。

**通則**：**凡是「一定會回傳東西」的機制，都要有一道拒絕它的關卡。**
檢索、模糊比對、最近鄰——它們沒有「查無此物」這個輸出，
所以必須由呼叫端來判斷「這個結果到底算不算」。

### 44. 會拒絕的防線，必須有東西可以退回

**症狀**：加了名稱檢查之後，「鮪魚蛋吐司」「雞胸肉便當」變成 **0 大卡**。

**原因**：配對 prompt 原本寫「**只在** source_ref 為 null 時填估算值」。
LLM 以為配上了就不填，程式端的防線卻把配對擋掉——**退路是空的**，整項變 0。

而 0 大卡是所有錯誤輸出裡最糟的一種：那一餐靜悄悄地不計入每日合計，
使用者完全看不出有東西漏掉。錯 4 倍至少看得出怪，0 連怪都不怪。

**對策**：改成**無論相不相符都要填自己的估算值**，當作被拒時的備案。
同一次呼叫，不多花錢。另外在程式端加一道：
熱量為 0 且未佐證的項目，在 note 寫明「無法估算，請手動修正」。

**通則**：**加一道會拒絕的檢查時，先確認被拒之後有什麼。**
只設計「通過」與「拒絕」兩條路不夠，要設計「拒絕之後怎麼辦」。
少了那一步，防線本身就成了新的故障點。

### 45. 多給模型的欄位，它會想辦法用上

**症狀**：配對那一步，「雞胸肉便當 500 公克」的估算值被填成 **45 大卡**。

**原因**：我在候選清單裡附了每 100 公克的營養素，想讓模型判斷得更準。
結果它把候選的每 100 公克值（雞胸骨湯 45 大卡）直接抄進「整項估算」欄位。
被名稱檢查擋掉之後，那 45 大卡就成了整份便當的數值。

判斷「這是不是同一種食物」**根本不需要營養素數字**——需要的是名稱、分類與配料描述。

**對策**：候選清單只給名稱、分類、配料描述，拿掉所有數字。
拿掉之後同樣的輸入估出 550 大卡（合理）。

**通則**：**只給模型做這個決定所需要的資訊。**
多給的欄位不是中性的，它會被納入推理，然後以你沒預期的方式出現在輸出裡。
這跟「prompt 塞越多越好」的直覺相反。

### 46. 一條路徑沒有 eval，就等於沒有品質保證

**順帶發現的最大缺口**：上面每一個坑都是**使用者問一句話才發現的**。

8 題 eval 全部在問答側（`/chat`）。`extract_food_log` 從 7 月寫到 10 月，
**從來沒有任何自動化檢查**——沒有 L1、沒有 judge、沒有人工標註。
所以「一杯鮮奶茶 50 大卡」這種錯誤可以存在三個月而沒人知道。

**對策**：純計算的部分先補單元測試（份量換算、名稱防線、缺值處理、
零熱量的標示），那些不花錢、不需要 LLM。至於「估得準不準」，
需要的是一組「輸入 → 可接受區間」的 eval 案例，列為下一步。

**通則**：**沒有 eval 的路徑，它的品質就是你最後一次手動測試的品質。**
而你會以為它跟有 eval 的那條一樣可靠，因為它們在同一個 repo 裡。

## 十一、工具層的四個坑

2026-11-05 補上 H 類的 `rank_my_meals` 與 I 類的 `category` 參數，
把兩個已知缺口關掉。過程中挖出四個新的，全部跟「工具與模型之間的介面」有關。

### 47. 工具失敗之後，模型會編，而且會挪用別的食物的真實編號

**症狀**：eval 的多跳題答案列出三樣點心，每樣都附了食藥署編號：

```
1. 蛋糕（草莓蛋糕）每 100 公克約 292 大卡 [I0410101]
2. 餅乾（巧克力餅乾）每 100 公克約 488 大卡 [I0410102]
3. 蛋酥（蛋酥餅乾）每 100 公克約 530 大卡 [I0410103]
```

**三樣食物和三個編號全部是編的。** 而 `I0410101` 是「雞絞肉」的真實編號，
被挪用到「草莓蛋糕」上。

**原因**：模型呼叫 `rank_by_nutrient(nutrient="calories")` 被白名單擋掉
（`ALLOWED_NUTRIENTS` 當時沒有 `calories`），兩次都失敗，手上沒有任何食物資料。
SYSTEM_PROMPT 寫了「工具失敗時用已取得的其他資訊盡量回答，並明確說明哪一部分查不到」，
它沒照做——**失敗的工具留下一個真空，而模型會把它填滿。**

**對策**：三層。
1. 把 `calories` 加進白名單（「熱量最低的點心」是這個工具最自然的用法，
   少一個選項的代價是一個看起來完全可稽核的假答案）
2. prompt 明講「工具失敗時絕對不要列出食物清單」「工具結果裡沒有的編號一個都不能寫」
3. **L1 的「引用標記真實存在」規則抓到了它**——那條規則就是為這件事加的

**通則**：**降級的指示不夠，要有人檢查降級有沒有發生。**
prompt 寫了規則不代表模型會遵守，而這類違規在輸出上看起來跟正常回答一模一樣。
唯一可靠的是確定性檢查：答案裡的每個編號，都必須在工具結果裡找得到。

### 48. 分類成「模型能修」卻不給它修的依據

**症狀**：模型把參數名打成 `"n nutrient"`（多一個空格），兩次呼叫都 TypeError，
然後回「看起來目前工具無法正確處理該請求」就放棄了。

**原因**：錯誤分類是對的——TypeError 屬於 `MODEL_FIXABLE_ERRORS`，
訊息會原樣回給模型重試。但 Python 的訊息是：

```
rank_my_meals() got an unexpected keyword argument 'n nutrient'
```

**它指出了什麼是錯的，沒指出什麼是對的。** 所以模型重試時犯了一模一樣的錯。
對照白名單的錯誤訊息（「可用值：['asc', 'desc']」）就看得出差別。

**對策**：TypeError 時用 `inspect.signature` 補上可用的參數名。

**通則**：**「可修復的錯誤」要附上修復所需的資訊，否則重試機會是白給的。**
檢查一遍每一種回給模型的錯誤訊息：它看完知道下一步該做什麼嗎？

### 49. 路徑對不代表答案對

**症狀**：上面那題（工具連續 TypeError、答案是「無法處理」）的
**路徑判準全部通過**——`required_tools` 有呼叫到、`forbidden_tools` 沒踩到、
`max_calls` 沒超。L1 判它通過。

**原因**：路徑判準檢查的是「呼叫了什麼」，不檢查「呼叫成功了嗎」。
這是 #28（只評答案不夠）的**鏡像**：先前防的是「答案對但路徑錯」，
沒防「路徑對但答案錯」。

**對策**：加一條確定性規則——**工具都呼叫過但每一次都失敗時，判失敗**。
不需要讀答案內容，只看 `ToolCall.error` 是否全部有值。
部分失敗不算（第一次錯第二次對是 agent 預期的重試行為）。

**通則**：**每加一個維度的判準，就要問它的反面有沒有人守。**
答案、路徑、效率——補了其中一個不代表另外兩個不會獨立失敗，
而「其中一個全綠」會讓人以為整體是好的。

### 50. 不要給模型比它被允許使用的更多資料

**症狀**：`rank_my_meals` 預設回傳 5 筆，模型把 5 筆全部列出來，超過字數上限。

**原因**：SYSTEM_PROMPT 寫「列出食物時最多 3 項」，工具預設給 5 筆。
**模型傾向用完手上的資料。** 兩個設定互相牴觸時，它照工具給的做。

順帶的二次效應：長度壓力下模型會開始砍東西，而它砍掉的是
「每 100 公克」這個計量基準——另一條規則的受害者。

**對策**：工具預設改成 3，跟 prompt 規則對齊。

**通則**：**prompt 的規則與工具的預設值要一致。**
不一致時模型照工具做，因為資料比指示具體。
改了 prompt 的數量限制，要回頭檢查每個工具的 `limit` 預設值。

## 十二、份量與結構：接上資料庫之後才出現的三個坑

2026-11-05，使用者在前端輸入「一碗泡麵」，系統記錄 **1420 大卡**（真實約 450）。
這三條都是「記錄側接上資料庫」之後才可能發生的——改版前 LLM 自己估，
不會有基準問題；接上資料庫之後，**數值準了，但單位可能對不上**。

### 51. 資料庫的「每 100 公克」指的是產品本身，不是你吃的那一碗

**症狀**：「一碗泡麵」記成 1420 大卡。

**原因**：

```
解析出的份量：300 公克   ← 煮好帶湯的一碗
資料庫的數值：473.3 大卡/100 公克   ← 乾燥麵塊加調味包
300 × 4.733 = 1420
```

食藥署量的是**產品如取樣時的狀態**。泡麵那一筆的鈉含量是 2077 毫克/100 公克，
一看就知道是乾燥產品——沒有人會喝到那麼鹹的一碗湯。
一包泡麵的乾重只有 85～100 公克，所以正確答案是 426 大卡。

**而名稱配對完全正確**（泡麵 ↔ 泡麵(牛肉口味)），所以 #43 那道名稱防線
攔不到——它防的是「配到別的食物」，這裡配對是對的，**基準錯了**。

這跟 #15 是同一個病根（「雞腿菇」35.8 vs「雞腿菇(乾)」297.6，差 8 倍）。
當時我把它寫進了文件，**但沒有寫進程式**。

**對策**：乾重參考放進**解析**那一步的 prompt——
份量是在那裡決定的（我第一版放在配對的 prompt 裡，位置錯了）。
配對那一步保留一個 `portion_g` 修正欄位當第二道防線，因為只有它看得到
候選的「前處理描述」。

**通則**：**接上權威資料來源之後，誤差從「數值」轉移到「單位」。**
數值對了會讓人鬆懈，但份量基準不一致的錯誤倍率更大——
LLM 自己估頂多差兩三倍，基準錯了可以差一個數量級。
每一個「× 份量 / 100」的地方都要問：這兩個 100 是同一個 100 嗎？

### 52. 多包一層巢狀，就多一個模型可以搞錯的地方

**症狀**：多項目的輸入讓 `POST /food_logs` 回 **500**。

**原因**：我把 response_model 從 `list[ItemMatch]` 包成 `{"matches": [...]}`，
理由是「instructor 對 `list[T]` 的支援不如單一 model 穩定」。
**那個理由是我憑印象編的**——這個專案最初的 `extract_food_log` 就是用
`response_model=list[FoodItem]`，跑了三個月沒出過問題。

包了之後，模型在多項目時回傳**扁平的單一物件**而不是帶 `matches` 的包裝，
instructor 重試四次全部失敗，`extract_food_log` 拋例外。
其中一次還把 `null` 回成字串 `"null"`——**結構一複雜，模型在各個維度上都開始出錯。**

**對策**：拿掉 wrapper，回到 `list[T]`。

**通則兩條**：
- **回應結構越扁平越可靠。** 每一層巢狀都是一個模型可能搞錯的地方，
  而結構錯誤會讓整個呼叫失敗，不像內容錯誤還有部分可用。
- **「我記得某個函式庫在這方面不穩」這種理由要查過再用。**
  我憑印象加了一層防禦，結果那層防禦本身成了唯一的故障點，
  而被我「防」的那個寫法在同一個 repo 裡已經穩定運作三個月。

### 53. 0 大卡是最糟的輸出，因為它會從合計裡消失

**症狀**：「午餐吃一碗泡麵＋梅花豬肉片」合計 **947 大卡**，少算了整塊豬肉——
那一項的熱量是 0。

**原因**：配對那一步的 prompt 要求「無論相不相符都要填自己的估算值」
（那是 #44 的對策），但模型**會漏**。漏掉的項目變成 0。

**0 比錯更難發現**：錯 4 倍看得出怪，0 連怪都不怪——
畫面上那一項還在，只是數字是 0，而使用者不會去核對每日合計的加法。

**對策**：加一個補估階段，只在真的有缺口時呼叫（多數記錄仍是兩次呼叫）。
它用的是**改版前那份單階段 prompt**——它還在版控裡、也還種在資料庫裡，
職責正好就是「估算營養素」，而且**不給它看候選清單**，
所以不會被資料庫的每 100 公克數值錨定（見 #45）。

補估失敗時保留 0 與「請手動修正」的提示：降級要誠實，
不要讓整筆記錄存不進去——使用者寧可看到「這一項估不出來」。

**通則**：**盤點每一個「可以是 0」的欄位，問它跟「不知道」要怎麼區分。**
數值型欄位的 0 同時表示「真的是 0」與「算不出來」，
而這兩件事對使用者的意義完全不同。

## 貫穿全部的一條原則

**最貴的 bug 不會報錯。**

上面第一節那四條、第三節的不確定性、第四節的 eval 陷阱，共同點都是
「程式跑完了、看起來正常、但結果是錯的」。對策也是同一套：

1. **主動加防呆**（`strict=True`、依 index 排序）——成本一行，省下數小時
2. **讓錯誤可稽核**（要求引用標記）——不求不出錯，但求查得出來
3. **量測而不是感覺**（TPR/TNR/kappa、跑 N 次看分布）——直覺對機率性系統無效
