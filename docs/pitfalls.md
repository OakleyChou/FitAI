# 踩過的坑

開發 FitAI 過程中實際遇到、花時間才搞清楚的問題。按「值得記住的程度」排序，
不是按遇到的時間順序。

每一條的格式是：**症狀 → 原因 → 對策**。
會報錯的坑很好解決；這份文件的重點是**不會報錯的那些**。

---

## 一、不會報錯的失敗（最危險）

這一類共同的性質是：程式跑完、沒有例外、輸出看起來正常，但結果是錯的。
除錯時最花時間，因為你不知道要從哪裡開始找。

### 1. Embedding API 回傳順序可能與輸入不一致

**症狀**：檢索結果莫名其妙地爛，但每一層看起來都正常——向量維度對、數量對、型別對。

**原因**：`client.embeddings.create()` 回傳的 `resp.data` 順序「文件說」會對齊 input，
但沒有保證。順序一旦錯位，就會變成「大麥仁的文字配到小米的向量」。

**對策**：依 `item.index` 排序後再取 `.embedding`。

```python
for item in sorted(resp.data, key=lambda x: x.index):
    vectors.append(item.embedding)
```

一行的成本，換掉一個查不出來的 bug。

### 2. `zip` 會靜靜截短到最短的那個

**症狀**：ingest 說「寫入 2213 筆」，資料庫實際只有 2180 筆，沒有任何錯誤訊息。

**原因**：`zip(texts, metas, vectors)` 在長度不一致時直接截短，不會抗議。

**對策**：Python 3.10+ 用 `zip(..., strict=True)`，長度不符就拋 `ValueError`。

### 3. 相對日期的測試資料會讓 eval 不可重現

**症狀**：昨天 eval 跑 80 分，今天同一份程式跑 60 分。以為 prompt 改壞了。

**原因**：seed 用 `days_ago=0` 產生「今天」的資料，隔天再跑，那批就變成昨天了，
「我今天吃了什麼」查不到東西。

**對策**：`run_eval` 開頭先呼叫 `seed()` 把 fixture 重置成已知狀態。
**eval 的第一要求是可重現，不是準確。**

### 4. `append` 一整批 vs `extend`

**症狀**：型別註記說 `list[list[float]]`，實際拿到 `[[Embedding, Embedding], [...]]`。

**原因**：`vectors.append(resp.data)` 是「把整個 list 當成一個元素塞進去」。

**對策**：接一整批用 `extend`，或在內層迴圈裡一次 `append` 一個。

### 5. 「查無此人」與「這個人沒資料」輸出一模一樣

**症狀**：`summarize_food_logs(user_id=999, ...)` 回傳「這段期間完全沒有飲食紀錄」——
跟真實存在但沒記錄的使用者輸出完全相同。

**原因**：查詢用 `WHERE user_id = 999` 篩選，篩不到就是空集合。
SQL 不會告訴你「這個 id 根本不存在」，因為它沒被問到這件事。

**為什麼要在意**：對 agent 來說這是實質差異。模型看到「沒有紀錄」會鼓勵使用者
開始記錄；看到「查無此帳號」則該說系統找不到人。輸出相同，模型就無從分辨。

**對策**：查資料前先確認主體存在。

```python
if db.query(User).filter(User.id == user_id).first() is None:
    return f"查無 user_id={user_id} 這位使用者。"
```

**通則**：只要函式對「空結果」和「查無對象」有不同的正確回應，
就不能讓兩者共用同一個輸出。這在資料層很容易混為一談，
因為 SQL 對兩者的回應都是空集合。

### 6. 工具的錯誤被包裝成結果後，失敗會偽裝成「模型不聽話」

**症狀**：agent 回答「豆漿熱量大約 40-60 大卡」——資料庫明明有 35 大卡的正確資料，
模型卻用自己的記憶回答。看起來像是 prompt 的「數值必須來自工具」規則沒生效。

**實際原因**：工具**根本沒跑成功**。

```
error = search_nutrition() got an unexpected keyword argument 'user_id'
```

迴圈對每個工具都注入 `user_id`，但只有查使用者資料的工具收這個參數。
而 `_execute` 刻意把例外包裝成「給模型看的錯誤訊息」（讓它能自我修正），
所以程式不會崩、使用者也看不出異狀——模型拿不到資料，只好用記憶回答。

**對策**：用簽章判斷該不該注入，而不是另外維護一份名單。

```python
if "user_id" in inspect.signature(func).parameters:
    safe_args["user_id"] = user_id
```

**真正的教訓**：把工具錯誤轉成模型可讀的訊息是對的設計，但它會**吃掉錯誤的可見度**。
沒有工具呼叫紀錄的話，症狀會指向完全錯誤的方向——當時差點去改 prompt。

所以 agent 一定要記錄每次呼叫的 `(工具, 參數, 結果, 錯誤)`。
這也是「評估路徑而不只評估答案」的前提。

### 7. 工具缺口不會讓模型說「做不到」，它會拿最接近的工具硬湊

**症狀**：問「我**吃過**什麼蛋白質密度最高的食物」，agent 回答柴魚片、小魚干——
那些是營養資料庫裡的食物，使用者根本沒吃過。兩次工具呼叫都成功（`error=None`），
答案讀起來也很順，但**回答的是另一個問題**。

**原因**：現有工具沒有任何一個能「在使用者自己的紀錄裡排序」。

| 工具 | 範圍 | 能排序嗎 |
|---|---|---|
| query_food_logs | 使用者紀錄 | ❌ 單日明細 |
| summarize_food_logs | 使用者紀錄 | ❌ 逐日彙總，不是逐食物 |
| rank_by_nutrient | **公開資料庫** | ✅ 但範圍錯了 |

模型只能用手上有的工具拼湊，於是挑了範圍錯誤的那個。
**它不會停下來說「我缺一個工具」——那不在它的選項裡。**

**對策**：定期用真實問句測試，並檢查**路徑**而不只是答案。
這類失敗只能從「它呼叫了什麼」看出來，因為答案本身看起來完全合理。

**通則**：agent 的能力邊界是隱形的。工具清單決定了它能回答的問題範圍，
但使用者不知道那個範圍，模型也不會主動宣告。
所以問句盤點要持續做——它是把隱形邊界顯形的唯一方法。

### 8. 漏掉一個 timeout，就等於整條請求沒有 timeout

**症狀**：把 Postgres 關掉測 agent 的降級行為，結果使用者看到的是
「查詢時間過長」——**降級那條路徑根本沒被走到**。模型從頭到尾沒機會回應。

**原因**：LLM 呼叫和迴圈總時間都設了上限，但**資料庫連線沒有**。
psycopg 預設會等到作業系統放棄，而且 `localhost` 會依序試 `::1` 和
`127.0.0.1` 兩個位址、各等一次。一次工具呼叫就吃光 90 秒的迴圈預算。

**對策**：

```python
engine = create_engine(
    settings.database_url,
    connect_args={"connect_timeout": 5},
    pool_pre_ping=True,
)
```

修完之後同樣的測試從「超過 90 秒然後逾時」變成「20 秒內給出降級回答」。

**通則**：**逾時控制的強度由最弱的那一環決定。** 你設了 LLM 的 timeout、
設了迴圈的預算，但只要鏈路上有一個對外呼叫沒設，它就會成為卡住整個
請求的那一個。列出所有對外呼叫（資料庫、LLM、檢索、外部 API），
確認每一個都有明確的上限。

`pool_pre_ping=True` 是附帶加的：連線借出前先 ping 一次，回收掉
已經斷掉的舊連線（例如資料庫重啟過）。代價是每次查詢多一次極輕量的往返。

### 9. Agent 的自主判斷，會放棄固定流程原本無條件會做的事

**症狀**：問「我吃的那個叫什麼粿的熱量多少？」，agent 一個工具都沒呼叫，
直接回「不太明確，請提供更具體的名稱」。同一題在舊的固定流程下是成功的。

**原因**：固定流程的檢索是**無條件執行**的——粉粿、芋頭粿早就在 context 裡，
模型只要照著報。換成 agent 之後，「要不要查」變成模型的判斷，
而它在**還沒查之前**就認定「太模糊所以查不到」。

諷刺的是，語意檢索正是為了處理模糊名稱而存在的（俗名寫進 content 就是
為了讓「洋薏仁」找到「大麥仁」），模型卻在用它之前就先放棄。

**對策**：prompt 明講「模糊名稱也要先查再說」，並說明理由——

```
不要在還沒查之前就判斷「太模糊所以查不到」
——那等於放棄了這個工具最擅長的事。
```

**通則**：從固定流程換成 agent，是把「一定會發生的事」變成「模型決定要不要做」。
**每一個原本無條件執行的步驟，都可能被跳過**，而且跳過時不會有任何錯誤。
換架構時要逐項檢查：原本必定發生的事，現在還會發生嗎？

### 10. 換架構會帶來系統性回歸，不是單一題的意外

**症狀**：eval 從固定流程改成跑 agent 之後，8 題裡有 4 題的答案長度超標
（285、239、279、280 字，上限 200）。

**原因**：工具回傳的是結構化 JSON，資訊量比檢索回來的文字 chunk 豐富得多，
模型傾向把查到的五項食物全部列出來——光列表就超過限制。

**對策**：找出真正的驅動因素再對症下藥。這裡不是「廢話太多」而是「列太多項」，
所以限制項數（「最多列 3 項」）比限制字數有效——**數項目比數字容易，
模型比較遵守得了**。同時把上限放寬到 300，因為列三項加說明確實需要那個長度。

改完之後四個長度失敗全部消失。

**通則**：換架構時不要只確認「新功能會動」，要**跑完整的回歸**。
單題測試會讓你以為只是偶發，跑完整套才看得出「8 題裡有 4 題」這種系統性模式。

### 11. 跨層的狀態旗標，沒有一路傳上來就等於不存在

**症狀**：把 Postgres 關掉打 `/chat`，agent 正確降級、回答也得體，
但回應裡的 `degraded` 是 `False`——前端會以為一切正常，不會提示使用者
有部分功能不可用。

**原因**：失敗的訊號在中途斷掉了。

```
_ToolOutcome.unavailable = True      ← 工具層知道
        ↓
ToolCall（沒有這個欄位）              ← 斷在這裡
        ↓
AgentResult.error = None             ← 只有迴圈本身失敗才設值
        ↓
API 層看不出有任何問題
```

`AgentResult.error` 只在**迴圈本身**失敗時才有值（最外層攔截、超過時間預算）。
個別工具失敗不會讓迴圈失敗——那正是降級設計的目的——但也因此，
API 層失去了「有東西壞掉」的資訊。

**對策**：把 `unavailable` 加進 `ToolCall`，API 層才判斷得出來。

```python
degraded = result.error is not None or any(c.unavailable for c in result.tool_calls)
```

**為什麼不能直接看 `ToolCall.error`**：那個欄位對「模型參數給錯」和
「重複呼叫」也會設值，兩者都不算服務降級。**需要的是專門的旗標，
不是拿現成的欄位湊合**——語意不同的東西共用一個欄位，遲早會誤判。

**通則**：分層架構裡，每一層都會決定「什麼要往上傳」。降級設計刻意讓
下層的失敗**不要**往上變成例外，但這樣一來，上層就需要**另一條明確的通道**
才知道發生過什麼。設計降級時要同時問：「上層要怎麼知道？」

這類 bug 單元測試抓不到——它跨了工具、迴圈、API 三層，每一層單獨看都正確。
只有真的把依賴關掉、真的打一次 API 才會浮現。

### 12. 「走了兩步」不等於「第二步用了第一步的結果」

**症狀**：問「我今天熱量還剩多少？可以吃什麼點心？」，agent 確實走了兩步，
答案裡的「還剩 380 大卡」也正確。路徑判準全部通過。但看參數：

```
query_food_logs(days_back=0)
rank_by_nutrient(nutrient="sugar_g", max_calories=150)
                                      ↑ 不是 380
```

`150` 是 docstring 裡「低卡」的建議門檻，**模型沒有把第一步算出的剩餘額度
接進第二步的參數**。答案裡引用了 380，工具呼叫卻沒用上它。

**為什麼危險**：這正是「有限迴圈 tool calling」這個架構決策的唯一依據。
如果多步只是「連續呼叫兩個工具」而沒有真正的資料依賴，那**路由就夠了**，
迴圈的成本白付。而只看路徑的話，這件事完全看不出來。

**路徑判準抓不到它**：

```
required_tools: [query_food_logs, rank_by_nutrient]   ✅ 通過
order:          [query_food_logs, rank_by_nutrient]   ✅ 通過
max_calls:      3                                     ✅ 通過
```

三條全過，但參數是錯的。

**對策**：加**參數斷言**。路徑判準檢查「呼叫了什麼」，還需要一層檢查
「帶了什麼參數」——例如「`max_calories` 應接近第一步結果中的剩餘額度」。

**通則**：**評估的粒度決定你看得到什麼。**
答案層看不到工具選擇，路徑層看不到參數正確性。每加一層都會揭露一批
先前隱形的失敗——而你不會知道還有幾層沒加，直到實際去看那一層的資料。

順帶一提，同一次呼叫裡 `nutrient="sugar_g"`（依糖分排序找點心）的推理也很可疑，
結果碰巧可用而已。這類「答案對但推理錯」只有逐項檢查參數才會浮現。

### 13. 工具只支援一個方向時，模型會硬用，然後把結果講反

**症狀**：問「我這週吃太多醣了嗎？有什麼低醣的可以換？」，agent 呼叫
`rank_by_nutrient(nutrient="carbs_g", max_calories=150)`，拿到**碳水最高**的
前三名，然後在答案裡寫「以下是三種碳水化合物含量較低的食物推薦」。

**原因**：那個工具當時只能由高到低排序，沒有 `order` 參數。
模型需要「最低」但工具只給得出「最高」——**它沒有拒答，而是照用不誤，
再在敘述層把結果講成相反的意思。**

**為什麼比拒答危險**：拒答至少誠實。這種失敗會給出一份看起來完全合理、
數字也真實存在的清單，只是意義整個相反。使用者沒有任何線索可以察覺。

**對策**：補上 `order` 參數（`desc` / `asc`），並在 docstring 與 JSON Schema
兩邊都明講什麼時候用哪個：

```
order: 這個參數決定你拿到的是最高還是最低，不要用錯。
       desc 用於「高蛋白」「纖維最多」；asc 用於「低醣」「低鈉」「最少」。
       用錯方向會拿到完全相反的清單，而它看起來仍然很合理。
```

**通則**：**檢查每個工具的「對稱性」**——支援最大值就該支援最小值、
支援升冪就該支援降冪、支援新增就該想到刪除。
缺了一半的話，模型不會提醒你，它會用手上有的那一半硬湊，
然後在自然語言層把差異抹平。這類缺口只有實際問「相反方向」的問題才會浮現。

## 二、向量檢索的本質限制

### 14. 語意檢索不會比較數值大小

**症狀**：查「高蛋白質的食物」，撈回鴨蛋白（10.8g）、雞蛋白（10.7g）——
而資料庫裡真正高蛋白的是柴魚片（76.5g）。

**原因**：向量比對的是「語意相似度」。「蛋白質」和「蛋白」在字面與語意上高度重疊，
模型被字面帶走。它從來就不理解「高」是一個數值比較。

**對策**：這類問題**不該用向量檢索**。改用 metadata 的數值排序：

```sql
SELECT content FROM knowledge_chunks
WHERE (meta->>'calories')::float < 150
ORDER BY (meta->>'protein_g')::float DESC LIMIT 5;
```

**延伸**：reranking 和 hybrid search（BM25）都救不了這題。
BM25 只會讓「蛋白」權重更高，錯得更徹底。改架構之前先確認病灶在哪。

### 15. content 怎麼組，比用什麼演算法重要

食藥署資料的兩個實例：

- **俗名有 40% 缺值，但有值時極重要。** 「大麥仁」的俗名是「小薏仁,洋薏仁,珍珠薏仁」。
  使用者打「洋薏仁」時，content 裡沒有這幾個字就永遠檢索不到。
- **樣品狀態決定數值對不對。** 「雞腿菇」35.8 大卡 vs「雞腿菇(乾)」297.6 大卡，
  差 8 倍，差別只在描述裡的「生」與「乾貨」。這欄不寫進 content，
  檢索回來的熱量會錯得離譜。

**對策**：ingest 之前先實際看資料的缺值分布與欄位語意，再決定 content 要放什麼。
這比調 chunk size 或換 embedding model 的效益大得多。

## 三、LLM 的不確定性

### 16. 同一個 prompt，不同次執行會有不同行為

**實測**：問句「我吃的那個叫什麼粿的熱量多少？」三次執行——

| 執行 | 結果 |
|---|---|
| 8/30 | ✅ 列出粉粿、芋頭粿與熱量 |
| 8/31 | ❌ 拒答「找不到相關資料」 |
| 9/02 | ✅ 列出候選 |

prompt 一個字都沒改。**單次執行的結果不能當結論。**

**對策**：重要的判斷要跑 N 次看通過率，而不是跑一次看對錯。

### 17. `temperature=0` 不保證穩定

**症狀**：LLM-as-Judge 對同一列給出不一致的判定。

**實測**：同一個輸入各跑 5 次——

```
預設溫度(1.0)   {'pass': 5}
temperature=0   {'pass': 2, 'fail': 3}
```

`temperature=0` 反而更不穩定。原因是這個判定本身落在**決策邊界**上，
而判準寫得模糊（「有說明份量假設」可解讀成「寫出份量」或「明講是假設」）。

**對策**：不穩定時先檢查**判準是否模糊**，不要急著調參數。
把判準改成「回答有明確寫出換算所使用的份量」之後就穩定了。

### 18. 規則修邏輯，範例修風格

**症狀**：prompt 裡寫了「不要提及使用者的飲食紀錄」，模型還是提了。

**原因**：那是**風格問題**不是邏輯問題。抽象規則對風格的約束力很弱。

**對策**：給一個 few-shot 範例，模型立刻照做。

```
Q：豆漿的熱量是多少？
A：無糖豆漿每 100 公克約 35 大卡 [1]，一杯 300ml 大約 105 大卡。
```

一個範例同時示範了：不提使用者紀錄、用「你」稱呼、引用格式、長度。

### 19. 過度嚴格的規則會造成過度拒答

**症狀**：檢索明明撈到粉粿和芋頭粿，模型卻回答「找不到相關資料」。

**原因**：prompt 寫了「絕對不要把營養資料庫的食物說成使用者吃過的」，
模型過度延伸成「連一般知識都不敢回答」。

**對策**：規則要區分情境。加上「問題類型判斷」——
一般知識問題只用資料庫回答、個人問題才看飲食紀錄。

### 20. 要求引用來源，能讓幻覺變得可稽核

**症狀**：模型回答「雞胸肉每 100g 含 31g 蛋白質」——資料庫裡沒有這筆，
而且跟資料庫的 24.8g 矛盾。要查證才知道是編的。

**對策**：在 context 給每筆 chunk 編號，要求引用時標註 `[n]`。

改變的不是「會不會出錯」，而是**錯誤的性質**：從「查不出來的編造」變成
「可以順著編號查證的引用」。而且引用標記可以用正則自動檢查。

### 21. 給模型的提示訊息，本身就是 prompt

**症狀**：重複呼叫的偵測反而讓答案變糟。模型第二次呼叫同樣的工具時，
迴圈回傳「這個查詢剛才已經做過了，結果如上」——模型接著就說「查無資料」，
改用自己的記憶回答。

**原因**：那句話是**寫給人看的**。模型讀到它，理解成「查詢沒有結果」，
而不是「去看前面那則訊息」。

**對策**：重複呼叫時回傳**快取的原結果**，不要回提示訊息。

語意上也更誠實——這個查詢的答案就是這個，再問一次答案不會變。

**通則**：任何會進到 messages 的字串都是 prompt，包括錯誤訊息、
狀態提示、佔位符。寫的時候要問「模型看到這句話會怎麼理解」，
而不是「這句話對人來說清不清楚」。

## 四、Eval 方法論

### 22. 整體一致率在類別不平衡下會騙人

**問題**：如果 90% 的輸出本來就是好的，一個「永遠回答 pass」的 judge
一致率就有 90%——但它完全沒用。

**對策**：分開看兩個方向，再用 Cohen's kappa 扣掉隨機一致。

| 指標 | 意義 |
|---|---|
| TPR | 人工判 fail 的，judge 抓到幾成（會不會漏放） |
| TNR | 人工判 pass 的，judge 沒誤報幾成（會不會亂咬） |

對 eval 的判官來說，**TPR 比 TNR 重要**——漏放會讓你以為系統沒事，
誤報只是多看幾筆。

### 23. 否定式判準會讓 judge 判反

**症狀**：判準寫「沒有提及今日飲食紀錄」，judge 的理由是
「答案沒有提到飲食紀錄」，然後判 **fail**。

**原因**：它把「觀察到判準描述的情況成立」當成了違規。

**對策**：判準一律用肯定式描述「通過時應有的狀態」：

```
沒有提及今日飲食紀錄
  ↓
回答內容完全來自營養資料庫，與使用者個人飲食紀錄無關
```

### 24. 判準必須正交

**症狀**：同一個缺陷被兩條判準各扣一次分，失敗率虛高。

**實例**：「所有被稱為高蛋白的食物須 ≥20g」和「每項食物都有檢索資料佐證」
同時懲罰「推薦了資料庫裡沒有的豆腐」。

**對策**：把其中一條收窄範圍，讓兩條各司其職。
前者改成「所有**從檢索資料中挑出**、被稱為高蛋白的食物…」。

### 25. 每次盯著資料修東西，那份資料就變成訓練資料

**症狀**：留出集跑出 100%，但那是因為我已經看著它修過兩次判準。

**原因**：這是統計上的老問題——**在測試集上調參**。

**對策**：資料集夠大時切出一批完全不看的樣本，只在階段性驗收時跑一次。
資料集還小的時候（<10 題），誠實的作法是**在報告數字時標註污染狀態**，
而不是假裝那是泛化能力。

### 26. 自動檢查的第一版一定不準

**症狀**：「數值有出處」規則示警兩次，兩次都是假警報——
`105`（= 35 × 3）和 `32`（= 96 − 64）都是合理的算術推導。

**對策**：兩件事。
一是**允許一步四則運算**（只允許一步，兩步以上任何數字都能湊出來）。
二是把還沒驗證過的規則列為 **warn 而非 fail**，避免它污染通過率、
久了讓人忽略所有警告。規則累積足夠精準度後再升級。

### 27. Judge 會反過來抓出人工標註的錯

校準時發現 judge 與人工不一致，追查後是**人工標錯了**——
同一題三條判準裡兩條標 fail、一條標 pass，邏輯上不一致。

校準是雙向的：你修 judge，judge 也幫你修標籤。

### 28. 「只評答案」在任何架構下都不夠，不是只有 agent 才要評中間層

**容易誤以為的事**：固定流程只有一條路徑，所以答案對就代表系統對；
要到換成 agent、有工具可選之後，才需要評估「中間發生了什麼」。

**這是錯的。** 固定流程一樣會「答案對但內部壞掉」。

**實例**（2026-08-27 實際發生）：

```
Q: 有什麼高蛋白低卡的食物？
A: 雞胸肉每 100g 含 31g 蛋白質…
```

答案讀起來完全正確——雞胸肉確實是高蛋白。但 31g 是模型從記憶裡拿的，
跟資料庫的 24.8g 矛盾；而檢索當時撈回來的其實是一堆蛋白（10.7g）。
**檢索壞了，只看答案完全看不出來。**

**正確的框架**：任何 LLM 管線都要評中間層，差別只在中間有什麼可評。

| | 要評的層 |
|---|---|
| 固定流程 | 檢索結果品質、答案有沒有基於它（groundedness） |
| Agent | 以上全部 **＋ 工具選擇（trajectory）** |

Agent 是**多了一層**，不是從「不用評」變成「要評」。

**兩種「路徑錯」的性質不同**：

```
固定流程：檢索撈到蛋白(10.7g)           ← 有撈，但撈得爛（品質問題）
Agent：  判斷「太模糊」直接不撈          ← 根本沒撈（結構問題）
Agent：  用 rank_by_nutrient 撈錯範圍    ← 撈了，但撈錯地方（結構問題）
```

後兩種在固定流程裡不可能發生，因為步驟是寫死的。

**對策**：固定流程時期就要有 groundedness 檢查（答案裡的數值能否在檢索結果中
找到），換 agent 時再疊上軌跡判準。這兩層分別對應 RAG triad 的
context relevance / groundedness，以及 agent 特有的工具選擇。

## 五、資料型別與序列化

### 29. JSONB 存不下 NaN

**症狀**：commit 時噴 `TypeError`，或存進去之後讀不回來。

**原因**：JSON 標準沒有 NaN 這個值。`json.dumps(float('nan'))` 產出的
字面 `NaN` 不是合法 JSON。

**對策**：`None if pd.isna(value) else float(value)`。

### 30. numpy 的 `float64` 不能被 json 序列化

同一行的另一半：`float()` 不只是防禦性轉型，是必要的——
pandas 取出的數值可能是 `numpy.float64`，`json.dumps` 不認識它。

### 31. `NaN != NaN`

**症狀**：用 `== None` 或 `is None` 判斷缺值，永遠判不到。

**原因**：IEEE 754 規定 NaN 不等於自己。

**對策**：用 `pd.isna()`。

### 32. content 與 meta 對缺值的處理應該相反

- **content**（給人和 LLM 讀的散文）：缺值**整項跳過**。
  不能出現「含膳食纖維 nan 公克」。
- **meta**（給程式讀的結構）：缺值**保留 key、值設 None**。
  這樣讀取端不會 `KeyError`，而且 `None` 明確表達「這項沒測」，
  跟「我忘了存這欄」區分得開。

同一份資料，兩種用途，兩種正確做法。

## 六、時區與日期

### 33. `timestamp without time zone` 遇上「今天」

**症狀**：查「我今天吃了什麼」，早餐不見了。

**原因**：`logged_at` 存的是 naive UTC，但使用者說的「今天」是台北時間的今天，
差 8 小時。直接用 UTC 的 00:00 當界線，會把**台灣時間早上 8 點前**的紀錄
算成前一天——而早餐正好落在這個區間。

**對策**：先在本地時區組出邊界，轉成 UTC，再脫掉 tzinfo。**順序不能顛倒**：

```python
dt.astimezone(timezone.utc).replace(tzinfo=None)   # ✅ 先換算，再脫標籤
dt.replace(tzinfo=None).astimezone(timezone.utc)   # ❌ 先脫標籤 → 時刻跑掉
```

`astimezone()` 是換算時刻，`replace(tzinfo=None)` 只是拔掉標籤、數字不動。

**根治**：欄位改成 `timestamptz`。但那是 schema 變更，需要 migration。

## 七、工具鏈的小坑

這些會直接報錯，查一下就解決，記錄下來只是為了下次快一點。

| 症狀 | 原因 | 對策 |
|---|---|---|
| `Relative module names not supported` | `python -m` 後面接了路徑 | 用點號模組名：`python -m app.rag.qa` |
| `ModuleNotFoundError: No module named 'app'` | 用檔案路徑跑，`sys.path[0]` 變成檔案所在目錄 | 一律用 `-m`，並在 `backend/` 執行 |
| 模組 docstring 失效（`__doc__` 是 None） | import 被放在 docstring 上面 | docstring 必須是檔案的第一個敘述 |
| `f-string: single '}' is not allowed` | f-string 裡有沒配對的 `}` | 檢查是否漏了左大括號 |
| f-string 裡的函式呼叫變成字面文字 | 運算式寫在 `{}` 外面 | 整個運算式要進大括號：`{round(x, 1)}` |
| `str(list)` 得到 `['a', 'b']` 這種東西 | `str()` 作用在容器上產生的是 repr | 用 `"".join(...)` |
| `AttributeError: 'DataFrame' object has no attribute 'limit'` | `.limit()` 是 Spark/SQL 的方法 | pandas 用 `.head()` |
| `df.head(None)` 型別檢查報錯 | 執行期可以，但簽章宣告是 `int` | 顯式寫 `if limit is not None` |
| instructor 包過的 client 沒有 `.embeddings` | instructor 只暴露 chat.completions | embedding 另開一個純 langfuse 包裝的 client |
| 讀 Excel 欄位全是 `Unnamed: N` | 第一列是說明文字，不是表頭 | `pd.read_excel(..., header=1)` |
| 連不上 5432 | Docker 容器重開機後停掉 | `docker start fitai-postgres` |

## 貫穿全部的一條原則

**最貴的 bug 不會報錯。**

上面第一節那四條、第三節的不確定性、第四節的 eval 陷阱，共同點都是
「程式跑完了、看起來正常、但結果是錯的」。對策也是同一套：

1. **主動加防呆**（`strict=True`、依 index 排序）——成本一行，省下數小時
2. **讓錯誤可稽核**（要求引用標記）——不求不出錯，但求查得出來
3. **量測而不是感覺**（TPR/TNR/kappa、跑 N 次看分布）——直覺對機率性系統無效
