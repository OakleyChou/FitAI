# 問句盤點

**用途**：在寫程式之前，逼出「系統要能做什麼」以及「現有工具介面缺什麼」。

這**不是** eval dataset。盤點只列問句與所需能力，不含判準、不需標註、不會被執行；
它的成本近乎零，所以可以寫得夠廣。eval dataset 則是每題要寫判準、每次執行要人工標註，
成本高得多，因此只收錄具代表性的問句（見文末的畢業條件）。

工具定義見 `backend/app/agent/tools.py`。

**這一類是「有限迴圈 tool calling」架構的存在理由。**

## E. 跨天聚合 → ⚠️ 現有工具做不到

`query_food_logs` 一次只查一天。這類問句需要跨日期範圍的聚合，
**是目前最明確的介面缺口**。

| # | 問句 | 需要什麼 |
|---|---|---|
| 15 | 我這週跟上週比，熱量有下降嗎？ | 兩個區間各自加總再比較 |
| 16 | 我最近三天平均吃多少蛋白質？ | 區間平均 |
| 17 | 我這週哪一天吃最多？ | 區間內逐日比較 |

**建議新增工具**：

```python
def summarize_food_logs(user_id: int, start_days_back: int, end_days_back: int = 0)
```

回傳區間內的逐日與整體統計。不要用「呼叫 query_food_logs 七次」來解決——
那會讓迴圈上限爆掉，而且七次查詢的結果要模型自己加總，正是我們一直避免的事
（加總邏輯放 Python 端，不讓 LLM 自己算）。

## F. 超出範圍 → 沒有工具，需要誠實拒答

| # | 問句 | 該有的行為 |
|---|---|---|
| 18 | 星巴克焦糖瑪奇朵的熱量？ | 食藥署資料庫沒有連鎖品牌品項，要說明查不到 |
| 19 | 我該不該吃減肥藥？ | 醫療建議，明確拒答並建議諮詢專業 |
| 20 | 我這樣吃會不會得糖尿病？ | 醫療診斷，同上 |

**這一類需要的是 system prompt 的規則，不是新工具。** 18 是資料涵蓋範圍的問題，
19、20 是安全邊界——目前 `qa.py` 的 prompt 完全沒有處理醫療建議的規則，這是個缺口。

## G. 記錄意圖 → 不是提問

| # | 輸入 | 問題 |
|---|---|---|
| 21 | 我剛吃了一個排骨便當 | 這是要**寫入**，不是查詢 |

使用者一定會在對話中直接這樣說。目前工具全部唯讀（刻意的決定）。

**決定（2026-09-02）：先用引導，暫不開放寫入工具。**

理由是風險不對稱——讀取工具選錯只是答錯、使用者一看就知道；寫入工具選錯會
默默把錯資料存進去，在對話流程裡很難撤銷。而延後的成本很低：
加一個新工具不會動到既有工具的介面。

實作上只需在 system prompt 加一條規則：

```
- 使用者描述剛吃的東西時（例如「我剛吃了排骨便當」），不要自行記錄，
  請說明你目前只能查詢，並引導他們使用飲食記錄功能。
```

之後要開放 `log_food` 的成熟度門檻：
1. 工具選擇準確率已經量測過（有數字，不是憑感覺）
2. 有確認步驟——先顯示將寫入什麼，使用者確認後才寫
3. eval 涵蓋寫入正確性

## 這份盤點抓出的缺口

| 缺口 | 類型 | 處理時機 |
|---|---|---|
| 跨天聚合沒有工具 | **介面** | 9/01 一起實作 `summarize_food_logs` |
| 醫療建議沒有規則 | **安全** | 9/01 加進 system prompt |
| 資料庫涵蓋範圍未說明 | **prompt** | 9/01，讓模型知道只有食藥署資料 |
| 記錄意圖沒有對策 | **產品決策** | ✅ 已決定：先引導，暫不開放寫入 |

前三個原本要等實際跑出錯才會發現。**盤點的價值就是把這些提前到寫程式之前。**

## 畢業條件：什麼時候該加進 eval dataset

符合任一即可：

1. 代表一種你在意的失敗模式
2. 你實際看過它出錯
3. 屬於核心使用情境
